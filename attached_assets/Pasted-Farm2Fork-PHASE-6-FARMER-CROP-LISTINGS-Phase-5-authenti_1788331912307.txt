3. FARMER AUTHORIZATION
==================================================

Only authenticated FARMER users can create/manage crop listings.

The authenticated Supabase user ID must determine the farmer.

NEVER trust a farmer_id supplied by the frontend.

FastAPI must obtain the authenticated user identity from the verified Supabase JWT.

Then resolve:

auth.users.id
    ↓
profiles.id
    ↓
farmers.profile_id
    ↓
farmers.id

All listing ownership must be tied to the authenticated farmer.

==================================================
4. CREATE CROP LISTING
==================================================

Implement:

POST /api/farmer/listings

The endpoint should create a crop listing belonging to the authenticated farmer.

Use only fields that actually exist in the current crop_listings schema.

The UI should support, where supported by the existing schema:

- Crop name
- Variety
- Quantity
- Unit
- Price
- Quality
- Location
- Harvest date
- Description
- Crop image

Do not invent database columns.

If a requested UI field does not have a corresponding database field, report it before modifying the schema.

Validate:

- crop name required
- quantity must be positive
- price must be non-negative
- required fields cannot be empty
- invalid dates rejected
- excessively large/unreasonable input rejected
- image type and size validated

Never trust price, quantity, farmer ID, or ownership information from the frontend without backend validation.

==================================================
5. GET FARMER'S LISTINGS
==================================================

Implement:

GET /api/farmer/listings

Return only listings belonging to the authenticated farmer.

Never return another farmer's private listing data.

Support useful information such as:

- crop name
- quantity
- price
- status
- location
- image
- created date
- updated date

Use pagination if the existing API architecture supports it.

==================================================
6. GET SINGLE LISTING
==================================================

Implement:

GET /api/farmer/listings/{listing_id}

The authenticated farmer may only access their own listing.

If the listing belongs to another farmer:

return HTTP 403 or 404 appropriately.

Do not leak another farmer's listing details.

==================================================
7. UPDATE LISTING
==================================================

Implement:

PUT/PATCH /api/farmer/listings/{listing_id}

A farmer can update their own listing.

Do not allow a farmer to change ownership.

Do not allow the frontend to change:

farmer_id

or any other ownership/security field.

Respect the existing allowed status values and database constraints.

==================================================
8. DEACTIVATE LISTING
==================================================

Implement a safe listing deactivation mechanism.

Use the existing crop_listings status field and its existing allowed values.

Do not physically delete the listing unless the existing product requirements specifically require deletion.

Prefer changing the listing to the existing inactive status.

Example:

ACTIVE
  ↓
INACTIVE

An inactive listing should not appear in the future buyer marketplace.

Do not invent a new status.

==================================================

Use the existing Supabase Storage bucket:

crop-images

The bucket is PRIVATE.

Do NOT make the bucket public.

Do NOT expose service-role credentials to React.

Do NOT expose SUPABASE_DATABASE_URL to React.

Implement secure image upload.

Recommended ownership structure:

crop-images/
    farmer-id/

Use authenticated ownership when generating upload paths.

Validate:

- allowed image formats
- maximum file size
- upload errors

Use signed URLs or the appropriate authenticated Supabase Storage mechanism for displaying private images.

Do not expose permanent public URLs for private images.
